# 3.4 Lita aldrig på indata, hantera fel på ett ställe

**Undantagen från "fel på ett ställe"**
git grep -n "res.status(500)" -- apps/api/src gav träffar i billing, customers, monsters, ravenPost, reports, stays och tournament. Förutom errorHandler själv ligger alla i legacy-mappen.

**Undantagen från "validera vid kanten"**
git grep -c "validate(" visade att tio route-filer i modules inte använder validate: audit, courier.owner, dashboard, jobs, notifications, owners, reports, search, settings och stays.routes.ts. Många har bara GET utan indata, men search använder söktexten i req.query utan zod.

**Varför finns undantagen i legacy?**
errorHandler var inte skriven då, så man hade felutskrivningarna direkt i routen: if (err) return res.status(500).send('oops'). Ingen ny kod ska läggas i legacy, så ingen har skrivit om dem.

**Vad ser användaren när felet inte går genom errorHandler?**
Användaren får bara oops, och eftersom det inte är JSON visar webben bara "request failed". Utvecklaren får ofta ingen logg, eftersom errorHandler aldrig loggar felet. Så var det med O'Brien i Felsökning 3.2: ingenting hände på skärmen, och felet syntes bara i terminalen för att db.ts loggade det. Det behövs en tydligare utskrift till användaren, och en logg till utvecklaren med tidsstämpel och kund-id, som jag kom fram till i Problemanalys 3.1.
